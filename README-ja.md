# philohash

English version: [README.md](README.md)

哲学の授業での研究：SHA-256 のようなハッシュ関数は汎用に設計されている。
ある一つの用途に特化したハッシュ関数なら、もっと良いものが作れるのではないか？

最初の一歩として SHA-256 を分解してみた。ビットの回転（ローテーション）を
AND や OR などの別のビット演算に置き換えると何が起こるか？

---

## レポート 1：SHA-256 のシグマ関数を置き換える

### 1. 背景

SHA-256 はメッセージを 64 バイトのブロックごとに処理する。各ブロックについて：

1. **メッセージスケジュール。** ブロックの 16 ワード `W0..W15` を 64 ワードに
   拡張する。新しいワードは *小シグマ* 関数 σ0 と σ1 を使って作られる：

   ```
   W[t] = σ1(W[t-2]) + W[t-7] + σ0(W[t-15]) + W[t-16]      (t = 16..63)
   ```

2. **圧縮。** 64 ラウンドかけて 8 つの状態ワード `a..h` を更新する。ラウンド `t`
   では `W[t]` と *大シグマ* 関数 Σ0、Σ1 を使う。

4 つの関数はすべて同じ形で作られている：

| 関数 | 定義 | 使われる場所 |
|---|---|---|
| σ0(x) | ROTR⁷(x) ⊕ ROTR¹⁸(x) ⊕ SHR³(x) | メッセージスケジュール |
| σ1(x) | ROTR¹⁷(x) ⊕ ROTR¹⁹(x) ⊕ SHR¹⁰(x) | メッセージスケジュール |
| Σ0(x) | ROTR²(x) ⊕ ROTR¹³(x) ⊕ ROTR²²(x) | 圧縮（`a` に適用） |
| Σ1(x) | ROTR⁶(x) ⊕ ROTR¹¹(x) ⊕ ROTR²⁵(x) | 圧縮（`e` に適用） |

ROTRⁿ は 32 ビットのワードを右に n ビット回転させる（はみ出したビットは左端に
戻ってくる）。SHRⁿ は右に n ビットシフトする（はみ出したビットは失われる）。
⊕ は XOR である。

**問い：** 回転と XOR は本当に必要なのか？ 他のビット演算でも同じくらい、
あるいはそれ以上にうまくいくのではないか？

### 2. 方法

**パターン。** 置き換えを 20 種類、3 つのグループに分けて作った。`t1, t2, t3` は
元の定義における、x を回転／シフトした 3 つのコピーである。

| グループ | パターン | 置き換え後 |
|---|---|---|
| — | `standard` | 本物の SHA-256（基準） |
| t1, t2, t3 の組み合わせ方を変える | `comb-and` | t1 & t2 & t3 |
| | `comb-or` | t1 \| t2 \| t3 |
| | `comb-and-xor` | (t1 & t2) ⊕ t3 |
| | `comb-or-xor` | (t1 \| t2) ⊕ t3 |
| | `comb-maj` | majority(t1, t2, t3) |
| | `comb-ch` | t1 ? t2 : t3（ビットごと） |
| | `comb-add` | t1 + t2 + t3 (mod 2³²) |
| 各回転／シフトを変える | `term-shr` | 右シフトのみ（回り込みなし） |
| | `term-shl` | 左シフトのみ |
| | `term-rotr` | 回転のみ（SHR も回転にする） |
| | `term-and-self` | x & ROT(x) |
| | `term-or-self` | x \| ROT(x) |
| | `term-xor-self` | x ⊕ ROT(x) |
| | `term-not` | ¬ROT(x) |
| | `term-and-mask` | x & 固定マスク（ビットが一切動かない） |
| 関数全体を置き換える | `whole-identity` | x |
| | `whole-zero` | 0 |
| | `whole-not` | ¬x |
| | `whole-mul` | x × 0x9e3779b1 (mod 2³²) |

あまり見かけない演算の意味。どれも 32 個のビット位置それぞれで独立に計算する：

- **majority(t1, t2, t3)**（多数決）：各出力ビットは、3 つの入力のうち 2 つ以上が
  その位置で持っている値（0 か 1）になる。式で書くと
  (t1 & t2) ⊕ (t1 & t3) ⊕ (t2 & t3)。SHA-256 自身も毎ラウンドこれを
  `Maj(a, b, c)` として使っている。
- **t1 ? t2 : t3（ビットごと）**、「選択」：t1 が 1 の位置では出力ビットを t2 から、
  t1 が 0 の位置では t3 から取る。式で書くと (t1 & t2) ⊕ (¬t1 & t3)。SHA-256 は
  毎ラウンドこれを `Ch(e, f, g)` として使っている。
- **ROT(x)** は、置き換え対象の元の項を同じ量 n のまま表す：回転の項なら ROTRⁿ(x)、
  σ のシフトの項なら SHRⁿ(x)。例えば `term-and-self` では σ0 は
  (x & ROTR⁷(x)) ⊕ (x & ROTR¹⁸(x)) ⊕ (x & SHR³(x)) になる。

4 ビットでの例：

| | ビット |
|---|---|
| t1 | `1 1 0 0` |
| t2 | `1 0 1 0` |
| t3 | `0 1 1 0` |
| majority(t1, t2, t3) | `1 1 1 0` |
| t1 ? t2 : t3 | `1 0 1 0`（前の 2 ビットは t2 から、後の 2 ビットは t3 から） |

各パターンを 3 つの **適用範囲** で試した：σ のみ（`small`）、Σ のみ（`big`）、
両方（`both`）。標準のものを含めて 61 個のハッシュ関数になる。それぞれを
フルの **64 ラウンド** で動かし、さらにフルの SHA-256 では隠れてしまう弱点を
見るために **24** ラウンドと **20** ラウンドでも動かした。

**テスト。**

| テスト | 問い | 理想値 |
|---|---|---|
| アバランシェ | `texts/` のファイルの 1 ビットを反転したとき、256 個の出力ビットのうち何割が変わるか？ | 0.5 |
| 最小アバランシェ | 上の最悪のケース。0 は異なる 2 つの入力が同じハッシュになったことを意味する。 | 約 100 ビット |
| SAC | 各出力ビットについて、反転する割合が 50% からどれだけずれているか？（最悪のビット） | 約 0 |
| 衝突 | `"0"` 〜 `"131071"` をハッシュし、24 ビットだけ残したときの衝突数をランダム関数と比べる | 1.0 倍 |
| ビットの偏り | 同じハッシュ群で、1 になる割合が半分からいちばんずれている出力ビットのずれ | 約 0 |
| スケジュールの混ざり具合 | ブロックの 1 ビットを反転したとき、`W16..W63` のビットの何割が変わるか？ | 標準：0.424 |
| 一対一 | σ0 を **2³² 通りすべての入力** で計算したとき、異なる出力はいくつか？ | 100% |
| 速度 | 8 MiB のデータでの MB/s | — |

失敗したテストごとに文字を付けて **WEAK** と表示する：
A アバランシェ、S SAC、C 衝突、F 実際の衝突を発見、B ビットの偏り、
W スケジュールの混ざり具合が 0.40 未満、L 情報が失われる（一対一でない）。

### 3. 結果

全出力：[`results/sigma_experiment.txt`](results/sigma_experiment.txt)
（と `.csv`）。64 ラウンドでのまとめ：

| パターン | 一対一 | スケジュールの混ざり具合（σ を置換） | σ のみ | Σ のみ | 両方 |
|---|---:|---:|---|---|---|
| **standard** | **100%** | **0.424** | ok | ok | ok |
| **term-rotr** | **100%** | **0.428** | ok | ok | ok |
| term-not | 100% | 0.424 | ok | ok | ok |
| term-xor-self | 50% | 0.433 | L | L | L |
| comb-add | 50.5% | 0.425 | L | L | L |
| comb-and-xor | 25.5% | 0.403 | L | L | L |
| comb-or-xor | 25.5% | 0.403 | L | L | L |
| term-shr | 12.5% | 0.155 | WL | L | WL |
| term-or-self | 6.5% | 0.405 | L | L | L |
| term-and-self | 6.4% | 0.406 | L | L | L |
| comb-maj | 4.9% | 0.387 | WL | L | WL |
| comb-ch | 3.4% | 0.387 | WL | L | WL |
| comb-or | 0.40% | 0.308 | WL | L | WL |
| comb-and | 0.19% | 0.209 | WL | L | WL |
| term-and-mask | 0.002% | 0.106 | WL | L | **ASCBWL** |
| term-shl | 12.5% | 0.114 | WL | SL | **ASCFBWL** |
| whole-identity | 100% | 0.110 | W | S | **ASCFBW** |
| whole-not | 100% | 0.074 | W | S | **ASCFBW** |
| whole-mul | 100% | 0.237 | W | S | **ASCFBW** |
| whole-zero | 0% | 0.021 | WL | SL | **ASCFBWL** |

#### 発見 1：生き残るのは回転 + XOR だけ

すべてのテストに合格したのは `standard`、`term-rotr`、`term-not` の 3 つだけだった。
`term-not` は実質的に新しいものではない。¬a ⊕ ¬b ⊕ ¬c = ¬(a ⊕ b ⊕ c) なので、
標準の σ の全ビットを反転しただけである。

AND や OR を使うパターンはすべて **情報を失う**：多くの異なる入力が同じ出力に
なってしまう。`comb-and` は取りうる値の 0.19% しか残らない。3 つの値の AND は
ほとんど 0 になるからである（出力ビットのうち 1 は 11% だけ）。XOR は特別で、
0 と 1 のバランスを保ち、回転と組み合わせると一対一になる。

#### 発見 2：フルの SHA-256 はほとんどの損傷を隠してしまう

σ だけを置き換えた場合、`whole-zero`（σ = 0）でさえ、**すべての** パターンが
ハッシュ出力のテストに合格した。Σ を使う圧縮ラウンドが十分に強く、それでも
出力をランダムに見せてしまう。

だからといって、それらが安全というわけではない。私たちのテストは出力が
ランダムに *見える* かどうかを調べるだけで、入力を慎重に選ぶ攻撃者は
シミュレートしていない。実際の攻撃はそうやって行われる。損傷はスケジュールの
テストで直接見える。例えば `W0` の最上位ビットを反転すると：

- 標準の σ：スケジュールの 1,536 ビット中 644 ビット（41.9%）が変わり、ほぼ
  すべてのワードに広がる；
- σ = 0：**12 ビット** しか変わらない（0.8%）。12 個のワードでそれぞれ 1 ビットずつ。

σ が弱いと、メッセージの小さな変化は小さいままである。そのため、差分が互いに
打ち消し合う 2 つのメッセージ、つまり衝突を探すのがずっと簡単になる。

#### 発見 3：ビットを右へ動かす演算がどこかに必要

最も悪い失敗は、ビットを下位の位置へ一切動かさないパターン（`whole-identity`、
`whole-not`、`whole-mul`、`term-shl`、`term-and-mask`、`whole-zero`）を σ と Σ の
両方に使った場合だった。64 ラウンドすべてを使っても：

- 出力ビットのうち変わるのは 50% ではなく約 25% だけ；
- `whole-identity`／両方 では、256 個の出力ビットのうち 7 個が **131,072 個の入力
  すべてで同じ値** だった；
- 24 ビットの衝突がランダムの約 48 倍起きた；
- **実際の衝突が見つかった**：入力の 1 ビットを反転しても、まったく同じハッシュに
  なった。

理由は、加算は情報を *左へ*（下位ビットから上位ビットへ）しか運ばないからで
ある。SHA-256 の中で上位ビットを下位へ戻す演算は回転だけである。回転がないと、
出力の下位ビットは入力の上位ビットに決して依存できない。

#### 発見 4：出力の品質には σ より Σ の方が重要

Σ だけを置き換えると、24 ラウンドと 20 ラウンドで出力の統計が崩れる（`whole-*`、
`term-shl`、`term-and-mask`、20 ラウンドでは `term-shr` も）。σ だけの置き換え
では一度も崩れない。なお 20 ラウンドでは、σ はスケジュールの 4 ワード
（`W16..W19`）にしか使われない。

#### 発見 5：速くなったパターンはない

64 ラウンドで標準の SHA-256 は 364 MB/s、出力テストに合格したパターンは
307〜384 MB/s で、測定誤差の範囲で同じだった。回転は CPU の 1 命令なので、
置き換えても何も節約できない。はっきり速くなったのは（最大 500 MB/s）Σ の処理を
削ったもの（`whole-identity`、`whole-zero`、`term-and-mask`）だけで、それらは
壊れている。速度を変えるのはラウンド数を減らすことであり、64 → 20 ラウンドで
約 3.8 倍速くなる（1,389 MB/s）。

#### 発見 6：全数調査はサンプリングに勝る

一対一テストの以前の版は 2²⁰ 個の入力をサンプリングしていた。その版は
`comb-add` を 100% 一対一と報告したが、2³² 個の入力をすべて調べると実際には
50.5% しか届かなかった。衝突する入力がサンプルに含まれていなかっただけである。

### 4. 結論

**SHA-256 の元の設計に勝った置き換えはなかった。**

最も良かったのは `term-rotr`（回転だけで作った σ）である。一対一で、すべての
テストに合格し、スケジュールの混ざり具合はわずかに良く（0.428 対 0.424）、
速度も同じだった。しかし SHR を取り除いてしまう。回転だけだと、入力を回転させると
σ の出力も同じだけ回転するだけになる。この対称性は攻撃者の助けになりうるが、
私たちの統計テストでは見えない。だから、より良いとは主張できない。

SHA-256 の回転と XOR は適当に選ばれたものではない：

- XOR は出力のバランスを保ち、回転と組み合わせると一対一になる；
- 情報を上位ビットから下位ビットへ動かす方法は回転しかない；
- SHR は回転の対称性を崩す。

### 5. 限界

- テストが測っているのは統計的なランダムさであり、攻撃への耐性ではない。
- アバランシェテストは `texts/` のファイル（約 5,800 回のビット反転）しか使っていない。
- 一対一のチェックは各パターンについて σ0 の量でのみ行い、σ1、Σ0、Σ1 では
  行っていない。
- 速度は他の作業も動いていた 1 台のマシンで測った。数値は ±10% 程度ばらつく。

### 6. 今後

σ を変えるだけでは、SHA-256 を *一般的に* 良くすることはできない。より有望なのは
**特定の用途** を選び、そこで許される妥協を受け入れる方向である。例えば
ハッシュテーブル用のハッシュは攻撃に耐える必要がないので、ラウンド数を減らしても
よいかもしれない。標準の SHA-256 を 20 ラウンドにしても、ここでのすべての
統計テストに 3.8 倍の速度で合格した。

## レポート 2：チャンクごとに異なる演算を使う

### 1. アイデア

SHA-256 はメッセージを 64 バイトの **ブロック**（チャンク）に切り、すべての
ブロックをまったく同じ方法で処理する。私たちのアイデアは、チャンクごとに処理を
変えて、処理を予測しにくくすることである。

1. **インデックスで：** チャンクの位置（0, 1, 2, ...）で演算を決める。
2. **内容で：** チャンク自身の値で決める。例えば値の mod 4 を計算し、
   用意した 4 つの演算から 1 つを選ぶ。

### 2. 方法

SHA-256 の圧縮関数の上に 20 種類の方法を作った。そのため結果の違いは、
チャンクごとの選び方だけから生まれる。「mod 4」で 4 つの選択肢から 1 つを選ぶ：

- Σ の回転量のセット 4 種類（セット 0 が SHA-256 のもの）；
- ラウンド定数表 K の開始位置 4 種類；
- ブロックの 16 ワードを読む順番 4 種類（BLAKE2 から借用）；
- ワード演算 4 種類：右に 7 回転、0x9e3779b1 を掛ける、`w ⊕ (w >> 13)`、
  0x6a09e667 を足す。どれも単独では一対一である。

| グループ | 方法 | 何が決め、何が変わるか |
|---|---|---|
| 基準 | `sha256` | ふつうの SHA-256 |
| インデックス | `idx-whiten` | ブロックのインデックスから作ったマスクを各ワードに XOR する |
| | `idx-counter` | ブロックのインデックスをラウンドの状態に混ぜる（BLAKE2 と同じ方式） |
| | `idx-rotset` | インデックス mod 4 で Σ の回転量セットを選ぶ |
| | `idx-constants` | インデックス mod 4 で K の開始位置を選ぶ |
| | `idx-permute` | インデックス mod 4 でワードの順番を選ぶ |
| | `idx-word-op` | (インデックス + ワードの位置) mod 4 で各ワードの演算を選ぶ |
| | `idx-all` | インデックス mod 4 で Σ セット、K の開始位置、ワードの順番をまとめて選ぶ |
| 内容 | `cnt-rotset` | ブロックのワードの和 mod 4 で Σ セットを選ぶ |
| | `cnt-constants` | 和 mod 4 で K の開始位置を選ぶ |
| | `cnt-permute` | 和 mod 4 でワードの順番を選ぶ |
| | `cnt-all` | 和 mod 4 で 3 つすべてを選ぶ |
| | `cnt-word-op` | **各ワード mod 4** でそのワードの演算を選ぶ |
| | `cnt-word-op-safe` | 同じだが、選択に使った 2 ビットを演算が決して変えない |
| | `cnt-word-rot` | 各ワードを（直前のワード mod 32）だけ回転する（RC5 暗号と同様） |
| | `cnt-round-select` | 毎ラウンド、状態の `e` mod 4 で Σ セットを選ぶ |
| | `cnt-chain-select` | それまでの全ブロックの結果 mod 4 で Σ セットを選ぶ |
| インデックス + 内容 | `idx+cnt` | (インデックス + 和) mod 4 で Σ セット、K の開始位置、ワードの順番を選ぶ |
| 並列 | `par-xor` | 各ブロックを別々にハッシュし、結果を XOR する（多くの CPU コアを使える） |
| | `par-xor-cnt` | 同じ。ブロックの内容 mod 4 で Σ セットを選ぶ |
| | `par-xor-idx` | 同じ。ブロックのインデックスを混ぜる（`idx-counter`） |

**テスト。** レポート 1 のテストすべてに加え、複数ブロックのメッセージ向けの
テストを追加した（テキストファイルのほとんどは 1 ブロックに収まるため）：

| テスト | 問い | 理想値 |
|---|---|---|
| 長いアバランシェ | ランダムな 1 KiB（16 ブロック）のメッセージの 1 ビットを反転したとき、変わる出力ビットの割合 | 0.5 |
| 入れ替え | hash(A ‖ B) と hash(B ‖ A) は等しくなるか？（ランダムなブロックの組 1,000 個） | 一度もない |
| 打ち消し | hash(A ‖ A ‖ C) と hash(B ‖ B ‖ C) は等しくなるか？（ランダムな 3 つ組 1,000 個） | 一度もない |
| 一対一 | ワード演算について、2³² 通りの全入力での異なる出力の数 | 100% |

新しいフラグ：M 長いアバランシェがずれている、X ブロックを入れ替えてもハッシュが
同じ、K 繰り返したブロックが打ち消し合った、L ワード演算が情報を失う。

64 ラウンド（フル）と 16 ラウンドでテストした。16 ラウンド未満は公平にテスト
できない。ラウンド t はワード t を読むので、一度も読まれないワードが出てしまう。

### 3. 結果

全出力：[`results/chunk_experiment.txt`](results/chunk_experiment.txt)
（と `.csv`）。

| 方法 | 64 ラウンド | 16 ラウンド | 64 ラウンドでの速度 |
|---|---|---|---|
| `sha256` | ok | ok | 250 MB/s |
| その他のインデックス方式すべて | ok | ok | 239〜254 MB/s |
| `idx-permute`、`idx-all` | ok | ok（ただし発見 4 を参照） | 245〜254 MB/s |
| `cnt-rotset`、`cnt-constants`、`cnt-word-rot`、`cnt-chain-select` | ok | ok | 246〜253 MB/s |
| `cnt-permute`、`cnt-all`、`idx+cnt` | ok | **B** | 245〜253 MB/s |
| `cnt-word-op` | **L：実際の衝突** | **L** | 194 MB/s |
| `cnt-word-op-safe` | ok | ok | 176 MB/s |
| `cnt-round-select` | ok | ok | 186 MB/s |
| `par-xor`、`par-xor-cnt` | **XK** | **ASMXK** | 247〜249 MB/s |
| `par-xor-idx` | ok | **ASM** | 250 MB/s |

#### 発見 1：フルの強さでは、測定できるほど良くなった方法はない

64 ラウンドでは、健全な方法はすべてのテストで SHA-256 と同じ数値になった。
レポート 1 と同様、フルの SHA-256 はこれらのテストに対してすでに完全に
ランダムに見えるので、追加した複雑さが改善として現れることはありえない。
複雑にすることは、測定できるほど良くなることを意味しない。

#### 発見 2：内容で選ぶと実際の衝突が生まれうる

`cnt-word-op` は取りうるワードの 28% を失い（到達できる出力は 71.9% だけ）、
実験では **フルの 64 ラウンドのハッシュ** で実際の衝突が見つかった。次の異なる
2 つの 4 バイトのメッセージは同じハッシュになる：

```
00 00 00 02  ->  2 mod 4 = 2  ->  w ⊕ (w >> 13)  = 0x00000002
00 00 01 00  ->  0 mod 4 = 0  ->  右に 7 回転     = 0x00000002
```

SHA-256 が始まる前に、どちらのワードも `0x00000002` になってしまう。その後は
2 つのメッセージが同一なので、ラウンドをいくら増やしても役に立たない。問題は、
演算が自分を選んだビットそのものを変えてしまえるため、この処理を元に戻せない
ことである。`cnt-word-op-safe` はその 2 ビットを変えずに残し、すべてのテストに
合格する。

内容で選ぶ方式には、私たちのテストでは測れない問題がさらに 2 つある：

- **攻撃者が演算を選べる。** メッセージを書く人はその値の mod 4 も決められるので、
  最も弱い演算を強制できる。設計の強さは、最も弱い選択肢の強さまでしかない。
- **タイミングの漏洩。** 演算によってかかる時間が違うと、時間を測ることでデータに
  関する情報が漏れうる。パスワードなどの秘密をハッシュするときに問題になる。

#### 発見 3：ブロックを別々に処理するときはインデックスが重要

SHA-256 では各ブロックの結果が次のブロックに渡されるので、ブロックの位置は
すでに意味を持っている。インデックスによる選択は、そこでは測定できる違いを
何も加えない。`idx-rotset`、`idx-constants`、`idx-permute`、`idx-all` は、
1 ブロックのメッセージでは SHA-256 とまったく同じになる。ブロック 0 は選択肢 0 を
使うからである（テストで確認済み）。

並列の設計は事情が違う。各ブロックを単独でハッシュするので、多くの CPU コアを
同時に使える：

- `par-xor`：2 つのブロックを入れ替えると **1,000 回中 1,000 回** 同じハッシュに
  なり、繰り返したブロックも 1,000 回中 1,000 回打ち消し合った。誰でも計算なしで
  衝突を作れる。
- `par-xor-cnt`：まったく同じ失敗。内容による選択は役に立たない。同じブロックは
  どこに置かれても同じ選択をするからである。
- `par-xor-idx`：失敗 0 回。ブロックの位置を区別できるのはインデックスだけである。

#### 発見 4：ラウンドを減らすと 2 つの弱点が現れる

16 ラウンドでは：

- **ワードの並べ替え。** `idx-permute` と `cnt-permute` は、実際のテキストの
  ワードを、メッセージの最後のブロックの **最終ラウンド** で読まれる位置へ
  動かしてしまうことがある。そのワードは 1 ラウンドしか混ぜられず、そのビットを
  1 つ反転しても出力ビットは **256 個中 2 個** しか変わらなかった
  （`texts/descartes_en.txt` で）。通常の SHA-256 では最後に読まれるのは長さの
  フィールドで、同じ長さのメッセージならすべて同じなので、こうしたことは起きない。
  内容で選ぶ版では、一部の出力ビットに偏りも生じた（B）。
- **最後の処理がない並列化。** 並列の設計はすべてアバランシェに失敗した。
  `par-xor-idx` でさえ、ブロックの最後のワードの反転で出力ビットが 3 個しか
  変わらなかった。ブロックの結果を圧縮の後に混ぜるものが何もないからである。
  逐次的な連鎖では、各ブロックの結果は次のブロックの圧縮で再び混ぜられる。
  並列の設計では、その役割を果たす圧縮を最後にもう 1 回加える必要がある。

#### 発見 5：速くなった方法はなく、ワードごとの演算選択は遅かった

ブロック単位で選ぶ方法は SHA-256 と同じ速度で動く。**各ワードについて内容で**
異なる演算を選ぶ方法（`cnt-word-op`、`cnt-word-op-safe`）は遅い。CPU がデータに
応じて分岐しなければならず、次にどの演算が来るか予測できないからである。
64 ラウンドで `cnt-word-op-safe` は 30%、`cnt-word-op` は 22% 遅く、16 ラウンドでは
それぞれ 65% と 51% 遅かった。内容に依存する量だけ回転する方法（`cnt-word-rot`）は
コストがかからなかった。それでも 1 命令で済むからである。

その他 2 つのケース：

- `cnt-round-select` はメインの実行では 26% 遅かったが、1 コアでの別の実行では
  3% しか遅くなかったので、この数値は不確かである。
- 16 ラウンドでは、`idx-whiten` と `idx-word-op` がそれぞれ 20% と 10% 遅かった。
  これは単に各ワードに追加の処理をしているためである。

### 4. 結論

- **内容で選ぶ方式：** おすすめしない。処理を元に戻せない場合に実際の衝突を生み、
  攻撃者に演算を選ばせてしまい、タイミングが漏れうるうえに遅かった。測定できる
  利点は何もなかった。
- **インデックスで選ぶ方式：** SHA-256 のような逐次的な設計では無害だが役に立たない。
  並列の設計では **不可欠** であり、ないとブロックを入れ替えたり打ち消したり
  できてしまう。

したがって最も有望な方向は `par-xor-idx`、つまりインデックスを混ぜた並列ハッシュで
ある。チャンクごとの演算がはっきり意味を持つ唯一の設計であり、複数の CPU コアを
使えば大きなファイルでずっと速くなる可能性がある。

### 5. 限界

- レポート 1 と同様、テストが測っているのはランダムさであり、攻撃者への耐性ではない。
- 速度は 1 コアで測った。並列設計の主な利点である複数コアの利用は、まだ測っていない。
- 試したのは「mod 4」による選択だけである。

### 6. 今後

`par-xor-idx` を本物の並列ハッシュにする。結合した結果を混ぜる最後の圧縮を加え、
ブロックを複数のスレッドでハッシュし、大きなファイルでの速度を SHA-256 と比べる。
それは元々の目標、つまり一つの用途（大きなファイル）に特化し、そこでは汎用の
SHA-256 より速いかもしれないハッシュ、に合致する。
